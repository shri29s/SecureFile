# Setup and startup

## Requirements

- Node.js 24 LTS and npm (tested with Node 24.15.0).
- Windows PowerShell for the supplied IPFS launcher. Core JavaScript services are portable, but the launcher assumes a Windows Kubo executable.
- A current browser with Ed25519 WebCrypto and IndexedDB support.
- Local ports 3001 (application), 5001 (Kubo API), 8081 (Kubo gateway), and 8545 (Hardhat).

Run commands from the repository root. Docker is not required.

## First installation

```powershell
npm ci
if ($LASTEXITCODE -ne 0) { throw 'Dependency installation failed' }
npm run setup
npm run compile
```

Setup creates `.env` with a random 256-bit master key and creates `data/`. It preserves an existing `.env`. Never commit `.env`; losing its master key makes the sealed database keys unusable.

Install the official Kubo Windows AMD64 release into `.runtime/kubo/`, so that `.runtime/kubo/ipfs.exe` exists. The tested release is **v0.43.1**:

```powershell
New-Item -ItemType Directory -Force .runtime | Out-Null
Invoke-WebRequest 'https://github.com/ipfs/kubo/releases/download/v0.43.1/kubo_v0.43.1_windows-amd64.zip' -OutFile .runtime/kubo.zip
$expectedDigest = 'c25871516dec4d97ce1d160a26c1e3fdad294cb0eea065c0c0343bcfca86c524'
if ((Get-FileHash .runtime/kubo.zip -Algorithm SHA256).Hash.ToLower() -ne $expectedDigest) {
    throw 'Kubo archive checksum mismatch'
}
Expand-Archive .runtime/kubo.zip -DestinationPath .runtime -Force
```

The checksum was obtained from the official release asset's SHA-256 metadata. If using another version, verify its own official checksum rather than this one.

## Start the services

Keep these three terminals open.

**Terminal 1 — local blockchain**

```powershell
npm run chain
```

Wait for the JSON-RPC server on port 8545.

**Terminal 2 — isolated local IPFS repository**

```powershell
powershell -ExecutionPolicy Bypass -File scripts/ipfs.ps1
```

The launcher initializes `.runtime/ipfs` when needed and starts Kubo offline. It does not publish to the public IPFS network. Wait for `Daemon is ready`.

**Terminal 3 — deploy and serve**

On the first run:

```powershell
npm run deploy
npm run build
npm start
```

Open [SecureFile](http://127.0.0.1:3001). In another terminal, `npm run health` should report `proxy`, `chain`, and `ipfs` as `true`.

For subsequent proxy-only restarts while the same Hardhat process remains running, use just `npm start`. Do not redeploy against an existing database: it binds to its deployment address.

## Development and tests

- `npm run dev`: Vite UI with API requests forwarded to the running proxy on port 3001.
- `npm run build`: rebuild the UI served by the proxy. Refresh the browser afterward.
- `npm test`: deterministic HTTP/SQLite/crypto tests without external services.
- `npm run test:integration`: uses real Kubo and a separate deployed contract on the local chain.
- `npm run bench`: creates scratch groups and compares lazy/eager revocation.
- `npm run bench:crypto`: local cryptographic microbenchmark.
- `npm run evaluation:report`: renders the evaluation report from both raw result files.

**Stop the proxy before live integration tests, then restart it afterward.** The current live test and proxy share the development chain signer. External test transactions advance its nonce and invalidate the running proxy's cached nonce. This does not require a database or chain reset. Do not run live tests and benchmarks concurrently.

## Restarting or resetting the blockchain

Hardhat state is in memory. Restarting it wipes all records. To begin a fresh demo:

1. Stop the proxy and Hardhat.
2. Start Hardhat again.
3. Set a new `DB_PATH` in `.env`, for example `data/demo-2.sqlite`.
4. Run `npm run deploy`, then `npm start`.
5. Create new browser identities or clear this site's IndexedDB using browser developer tools.

Keep old databases and their matching master key if their data matters. No reset command silently deletes them. Redeploying to the same deterministic address after a chain restart does not restore old records.

## Configuration

| Variable | Default / role |
| --- | --- |
| `PORT` | 3001; proxy listens on loopback |
| `DEMO_MODE` | 1 enables public ciphertext endpoint and eager-mode comparison |
| `RPC_URL` | `http://127.0.0.1:8545` |
| `PROXY_PK` | Public Hardhat account 0 key, local development only |
| `PROXY_MASTER_KEY` | Required 64 hex characters; generated by setup |
| `IPFS_API` | `http://127.0.0.1:5001` |
| `DB_PATH` | `data/sfs.sqlite` |
| `REENCRYPT_T` | 3; migration triggers when version gap is greater than T |
| `MAX_UPLOAD_MB` | 100 at proxy; browser limits individual files to 50 MiB |

## Troubleshooting

| Symptom | Action |
| --- | --- |
| Connection refused / red health indicator | Start the corresponding service and check its port |
| Missing `deployment.json` | Start Hardhat, then run `npm run deploy` |
| Missing contract artifact | Run `npm run compile`; compilation uses pinned local solc |
| Master key does not match database | Restore the matching `.env`; do not replace its key |
| Chain/database mismatch | Use a fresh database with the fresh chain; preserve old files |
| `NONCE_EXPIRED` after live tests | Stop/restart the proxy to refresh its signer nonce |
| `UNKNOWN_USER` after reset | Create a new browser identity or clear stale IndexedDB identities |
| Old file downloads as `.bin` | Its original name was not saved; re-upload with the current client |
| Native SQLite installation fails | Use supported Node 24, then retry `npm ci`; building from source may need Windows C++ build tools |

Stop each service with Ctrl+C in its terminal. Keep `.env`, SQLite database/WAL files, Kubo repository and chain lifetime consistent; see [implementation limits](implementation-limits.md).
